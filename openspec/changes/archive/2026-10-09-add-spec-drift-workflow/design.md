# Design: add-spec-drift-workflow

## Context

`pnpm spec:check` (bajo `scripts/spec-watch/`) ya implementa el chequeo de deriva con sus códigos de salida (0 sin diferencias, 1 con diferencias, 2 fallo operativo/canario) y su informe de severidad fija. La main spec de `spec-integrity` y el README de `packages/sdk/schemas/` anticipan un job futuro que dé la semántica "última ejecución del job" a `lastSyncedAt`; este cambio es la **fase 1** de ese job (solo detección y reporte — INDENT 5.4, 7). El repo ya usa GitHub Actions para CI (lint/typecheck/build/test en Node 22 y 24). Ver `proposal.md` — Why.

## Goals / Non-Goals

**Goals:**

- Detección mensual automática de deriva en las superficies oficiales, con issue `spec-drift` como canal visible.
- Deduplicación por huella del informe: una deriva persistente produce un issue y comentarios, no spam.
- Garantías estructurales de no-mutación (sin commit, PR, `spec:update` ni cambio de `currentSet`).

**Non-Goals:**

- Vendorización automática (`spec:update` sigue siendo manual, con revisión humana del diff).
- Cambiar la semántica de `lastSyncedAt` en el manifiesto (eso llega cuando el job ejecute `spec:update` — fase posterior).
- Notificaciones fuera de GitHub Issues (Slack, email).
- Ejecutar el job en forks o repos con credenciales de Hacienda.

## Decisions

- **D1 — Un solo workflow `.github/workflows/spec-drift.yml`**: `runs-on: ubuntu-latest` (trae `gh` preinstalado y no requiere `xmllint` ni otros binarios — **verificado**: el camino de `spec:check` (`check-core.mjs` y su grafo de imports: discover/analyze/probe/http/canary/report/parse/manifest) usa solo `node:*` y `fetch`, sin `child_process`; el único `execFileSync` del paquete está en `update.mjs` y lanza `node` sobre `spec-verify.mjs` — fuera de este job), `schedule: cron "0 12 1 * *"` (día 1, 12:00 UTC = 06:00 Costa Rica — evita la medianoche local, hora en la que un fallo nadie lo ve hasta la mañana) + `workflow_dispatch`, con `concurrency: { group: spec-drift, cancel-in-progress: false }` para que un dispatch solapado espere al cron en curso en lugar de correr en paralelo y duplicar issues. Checkout, Node 22, `corepack enable`, `pnpm install --frozen-lockfile`, ejecución de `pnpm spec:check` capturando stdout/stderr en un archivo y el código de salida en una variable (el paso no debe abortar con `set -e` antes de leer `$?`). Nota: `schedule` solo corre en la rama por defecto del repo; los forks no heredan el cron (comportamiento estándar de GitHub, no requiere lógica extra). _Alternativa descartada_: workflow existente de CI con job condicional — acoplaría deriva (mensual, red externa) a CI (por push/PR, sin red a Hacienda).
- **D2 — Permisos mínimos**: `permissions: { contents: read, issues: write }`. El token no puede commitear ni abrir PR de forma estructural (refuerza el requisito de no-mutación). _Alternativa descartada_: PAT con más permisos — innecesario para issues en el mismo repo.
- **D3 — Huella del informe**: SHA-256 (hex) del cuerpo del informe con el texto normalizado (solo `trim` de whitespace **final** por línea; la indentación inicial es parte de la estructura del informe — secciones anidadas — y normalizarla enmascararía cambios reales de formato; un cambio de indentación futuro implicaría un formato nuevo y una huella nueva, que es el comportamiento deseable). **Verificado contra `scripts/spec-watch/lib/report.mjs` en la rama del job: el informe no contiene timestamps ni datos volátiles** (solo path, versión, URLs, hashes y kind/surface), así que la huella es estable entre corridas para la misma deriva. _Efecto a documentar en el README de schemas_: si alguien reformatea el reporter por una razón ajena a la deriva (p. ej. cambia la indentación), la huella del informe cambia y el job abrirá **un issue nuevo una vez** aunque la deriva sea la misma — se cierra el viejo a mano; el dedupe no protege contra cambios de formato del propio informe. El workflow incrusta la huella en el issue como comentario HTML invisible: `<!-- spec-drift-fingerprint: <sha> -->`. El deduplicador lista issues **abiertos** con la etiqueta `spec-drift` (`gh issue list --label spec-drift --state open --json number,body`), extrae huellas con un parser defensivo (issues **sin** el marcador — creados a mano o antiguos — se ignoran, no fallan la corrida), compara y comenta con `gh issue comment` si hay match; si no, `gh issue create --label spec-drift`. Al abrir un issue **nuevo**, si ya existen otros issues `spec-drift` abiertos con huella distinta, el cuerpo los referencia ("Relacionado con #N…") para dar contexto al revisor. _Alternativa descartada_: título determinista como clave — visible y frágil ante cambios de formato; búsqueda de texto completo de GitHub — semántica opaca y con límites de índice.
- **D4 — Etiqueta garantizada**: antes de abrir el issue, `gh label create spec-drift --force --color B60304 --description "Hacienda spec drift detected by spec:check"`. El flag **existe y está verificado en el manual oficial de `gh`** (`cli.github.com/manual/gh_label_create`: `-f, --force` — "Update the label color and description if label already exists"). Sin él, `gh label create` **falla** si el label ya existe con color o descripción distintos (un `|| true` ciego ocultaría el fallo y no garantizaría el color). Con `--force`, una corrida posterior reaplica la definición canónica. _Alternativa descartada_: `gh label create ... || gh label edit ...` — equivalente más verboso ahora que `--force` está confirmado; crearla a mano en el repo — se pierde en renombres/forks.
- **D5 — Ramificación por código de salida**: `0` → success sin issue; `1` → ruta de issue; `2` o **cualquier código distinto de 0 y 1** (p. ej. 127 = command not found) → fallo operativo: imprimir `spec:check falló con código <N>: <stderr>` y salir **siempre con 2** (los consumidores del job solo deben esperar 0/1/2; el código original viaja en el mensaje, no en el exit code), **sin** tocar issues. El veredicto `sin cambios` jamás se emite en la rama de fallo: sale del propio `spec:check`, que ya lo prohíbe en su canario, y el job no lo reescribe. Para el mensaje de superficie caída el job **no parsea ni reformatea**: emite el stderr de `spec:check` tal cual, y los mensajes del canario siempre incluyen `superficie <id>` (verificado en `scripts/spec-watch/lib/canary.mjs`). La garantía se reparte así: **el job preserva el stderr; `spec:check` garantiza nombrar la superficie**. Si `spec:check` cambiara y dejara de nombrarla, el workflow no lo detecta — es un contrato de la capacidad `spec-integrity` vigente, no del workflow.
- **D6 — `gh` CLI en el runner**: los runners de GitHub traen `gh` autenticado con `GH_TOKEN: ${{ github.token }}`. _Alternativa descartada_: `actions/github-script` con REST — más verboso sin ganar nada para 3 operaciones.
- **D7 — Sin caché ni estado entre corridas**: cada ejecución es stateless; la deduplicación vive en los issues abiertos. _Alternativa_: artefacto con la última huella — un solo punto de fallo y no visible para humanos.
- **D8 — Fallos del canal de reporte no se confunden con "sin cambios"**: toda operación de `gh` (label, list, comment, create) chequea su código de salida; si alguna falla (token, API de GitHub caída, rate limit), el job termina con error claro que name la operación fallida y código 2 — nunca success y nunca el veredicto `sin cambios`. Para garantizarlo técnicamente, el veredicto de `spec:check` solo se emite en stdout **en la rama 0** (success); la rama 1 imprime el informe como parte del issue, no como veredicto del job — así un fallo posterior de `gh` no puede dejar "sin cambios" ni un veredicto ambiguo en el stdout del job. Un fallo de red de GitHub es "no pude reportar", no "no hay deriva". _Alternativa descartada_: ignorar errores de `gh` con `|| true` — dejaría un job verde sin issue cuando sí hay deriva.
- **D9 — Límite de tamaño del informe**: el cuerpo del issue/comentario se trunca a ~60 KB (por debajo del límite de ~65 KB de GitHub) con una nota final explícita (`[informe truncado — completo en los logs del job]`); el informe íntegro siempre queda en el log de la corrida. _Alternativa descartada_: subir el informe como artefacto del workflow — los artefactos caducan y requieren permisos extra; el log ya persiste con la corrida.
- **D10 — Deriva parcial con una superficie caída: se hereda el cortocircuito de `spec:check`**. Verificado en `scripts/spec-watch/lib/check-core.mjs`: cualquier fallo de canario corta antes del análisis y devuelve código 2 con findings vacíos — si `atv` y `ovi` tuvieran deriva y `cdn` está caída, no hay informe parcial, hay fallo operativo. El workflow **propaga** esa decisión sin tocarla: rama 2 → fallo, sin issue. Consecuencia aceptada en fase 1: un mes con superficie caída puede ocultar deriva parcial; la deriva real aparecerá en la primera corrida con todas las superficies sanas (el dedupe por huella absorbe la repetición). _Explícitamente fuera de alcance_: cambiar el cortocircuito del canario para analizar superficies accesibles — eso es un cambio de comportamiento de `spec:check` con su propio delta en `spec-integrity`, no del workflow; queda como candidato de backlog.

## Risks / Trade-offs

- [Superficie de Hacienda inestable o WAF/CDN bloquea runners de GH] → el job falla (código 2) con mensaje claro; se reintenta con `workflow_dispatch`. El bloqueo previo de UA de navegador ya está documentado y `spec:check` usa agentes tipo curl. **Mitigación de proceso**: validar el acceso real desde el runner **antes del merge** (task 4.6); si el bloqueo aparece, documentarlo y decidir runner propio o coordinar con el tutor — no mergear un workflow inútil.
- [Fallo de la API de GitHub durante el reporte] → D8: el job falla con error distinto de "sin cambios"; se reintenta con `workflow_dispatch` una vez la API responda.
- [Huella inestable si cambia el formato del informe] → el informe tiene orden de secciones fijo (spec de `spec:check`); cambios de formato futuros pueden abrir un issue nuevo una vez — aceptable y visible.
- [Spam de issues si el dedupe falla] → solo la etiqueta `spec-drift` dispara comentarios/issues; `contents: read` impide que el job haga más daño; cierre manual + reapertura por nueva huella.
- [Cron en UTC puede no caer en día "local"] → documentado en el workflow; se ajusta el cron si el equipo quiere otra ventana.
- [Issues creados por `github-actions[bot]` no asignan revisor] → el label es el canal de filtrado; la asignación queda para el equipo (fuera de alcance).

## Migration Plan

1. Merge del workflow a `main` → se activa el cron solo en la rama por defecto del repo.
2. Primera verificación **antes del merge**: `workflow_dispatch` sobre una rama del repo principal (el cron no corre en forks ni en ramas distintas a la por defecto); probar los tres caminos — `spec:check` con 0 (success sin issue), deriva simulada **modificando un `sha256` en el manifiesto de la rama de prueba** (issue + dedupe) y con superficie inaccesible (fallo sin issues). Cerrar el issue abierto y re-disparar para validar el dedupe con issue cerrado (task 3.6). Confirmar además que el runner alcanza las tres superficies de Hacienda.
3. Rollback: borrar el archivo del workflow (o desactivarlo en la pestaña Actions); los issues ya abiertos se cierran a mano.
