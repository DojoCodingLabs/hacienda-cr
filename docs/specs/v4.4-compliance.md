# Spec: Hacienda v4.4 Compliance & 2026 Readiness

**Status:** Draft · **Date:** 2026-08-24 · **Owner:** TBD

## Why now

Two independent problems, one deadline:

1. **We are non-compliant with base v4.4 today.** Our document builders emit the **v4.3 document body** under v4.4 namespaces. Verified against the official `FacturaElectronica_V4.4.xsd` (downloaded 2026-08-24 from ATV, `docs/esquemas/2024/v4.4/`): the schema requires `ProveedorSistemas` and `CodigoActividadEmisor` (we emit neither), renamed `Codigo` → `CodigoCABYS` in line items, moved `MedioPago` into `ResumenFactura`, and renamed fields across Exoneración, OtrosCargos, and InformacionReferencia. Any document we build should fail Hacienda's XSD validation.
2. **The April 22, 2026 revision of v4.4 becomes mandatory November 1, 2026.** It makes the clave and cédulas jurídicas alphanumeric, adds reference codes 13–17 and referenced-doc types 19–20, and relaxes phone/decimal restrictions. (Announced via TRIBU-CR OVi comunicado; corroborated by KPMG CR, Gosocket, LLB.)

The REST API surface is unaffected: base URLs, IDP realms (`rut`/`rut-stag`), client IDs (`api-stag`/`api-prod`), and token flow are unchanged by the TRIBU-CR migration.

### Ground truth used by this spec

- Official 2024 v4.4 XSDs downloaded from `https://atv.hacienda.go.cr/ATV/ComprobanteElectronico/docs/esquemas/2024/v4.4/` (all 9 files). These are the **base** v4.4 schemas: clave still `\d{50}`, reference codes stop at 12/18.
- The April 2026 revised XSDs are distributed via the TRIBU-CR OVi portal ("Comprobantes Electrónicos y Tico Factura") and must be fetched there (Workstream 2, task 2.1). Until then, 2026-revision details marked _(vendor-reported)_ need confirmation against the official files.

### 1.9 Per-document-type deltas

- **REP (`ReciboElectronicoPago_V4.4.xsd`)** has a _reduced_ schema: root = `Clave, ProveedorSistemas, NumeroConsecutivo, FechaEmision, Emisor, Receptor, CondicionVenta, DetalleServicio, ResumenFactura, InformacionReferencia…` — **no `CodigoActividadEmisor`**, simplified `LineaDetalle` (`NumeroLinea, Detalle, MontoTotal, SubTotal, Impuesto, ImpuestoNeto, MontoTotalLinea` — no CABYS), simplified `ResumenFactura`. The generic `buildStandardDocumentBody` cannot serve REP; give `recibo-builder` its own body function against the REP XSD.
- **MensajeReceptor** fields per XSD: `Clave, NumeroCedulaEmisor, FechaEmisionDoc, Mensaje, [DetalleMensaje], [MontoTotalImpuesto], CodigoActividad, CondicionImpuesto, [MontoTotalImpuestoAcreditar], [MontoTotalDeGastoAplicable], TotalFactura, NumeroCedulaReceptor, NumeroConsecutivoReceptor`. Diff our `MensajeReceptor` builder against this list (note: cédula fields here are the ones renamed to ≤20-char strings in the 2026 revision).
- **FEE (Exportación)** and **FEC (Compra)**: re-derive required/optional fields from their own XSDs after the shared changes (e.g. FEE has no receptor-ID requirement; FEC swaps emisor/receptor roles).
- **Doc types 08 (Compra de Pago) / 09 (Gasto de Viaje)**: still no XSD published for these in the v4.4 package; keep as enum-only, document as not implementable yet.
- **Currencies**: `CodigoMonedaType` is the full ISO-4217 enum (~160). Replace the 3-entry list in `shared/src/constants/currency-codes.ts` and tighten the schema from "any 3 chars" to the enum.

### 1.10 Signature layer

`ds:Signature` is `minOccurs=1 maxOccurs=5` in every v4.4 XSD (base package already allows 5). Our single XAdES-EPES signature remains valid; ensure the validator/parser tolerates 1–5 signatures. XAdES policy hash `Ohixl6upD6av8N7pEvDABhEL6hM=` stays; see 3.5 for the URI cleanup.

Vendor-reported "Signature 1→5", phone relaxation, and decimal widening claims are NOT in the schemas (Signature was already 1..5 in the 2024 base). Note: `IdentificacionType.Numero` was already a free string ≤20 in the base XSDs, so no schema change was needed for alphanumeric cédulas — our per-type digit validation for types 01–04 remains stricter than the XSD pending official guidance on the new Registro Nacional format (2.3, open).

**Remaining**: `DetalleSurtido` / `DatosImpuestoEspecifico` modeling (deferred), sandbox end-to-end smoke test, cédula-jurídica format rule for the alphanumeric registry IDs (~Q4 2026).

Additional XSD findings confirmed during implementation (beyond §1):

- Namespaces are lowerCamelCase (`…/v4.4/facturaElectronica`); XSD filenames are `*_V4.4.xsd` (no dot).
- `Barrio` is free text 5–50 chars in v4.4 (no longer a 2-digit catalog code); `OtrasSenas` is required, 5–250 chars; `Detalle` min 3 chars.
- Per line, `BaseImponible`, `Impuesto` (≥1), `ImpuestoNeto`, and (FE/TE) `ImpuestoAsumidoEmisorFabrica` are **required**; FEE lines omit BaseImponible/ImpuestoNeto entirely; REP lines are reduced to 7 elements.
- `CodigoTipoMoneda` is required in every ResumenFactura.
- REP: `CondicionVenta` enum is only `09`/`11` (payment codes); its `InformacionReferencia.Numero` is required; Emisor/Receptor are minimal (Nombre/Identificacion/Correo).
- `NombreInstitucion` (exoneración) is a coded enum `01`–`12`, `99` (answers old question 2); `IVACobradoFabrica` is a code (`01`/`02`), not an amount.
- Emisor `CorreoElectronico` allows 1–4 entries; Receptor allows exactly one.

## Open questions

1. `ProveedorSistemas` value: currently defaults to the emisor's cédula in CLI/MCP. ANEXOS says the _software provider's_ ID — decide the proper default + a `provider_id` key in `config.toml`.
